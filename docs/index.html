usque · MASQUE / Connect-IP client

Cloudflare WARP for your OpenWrt router.

usque is a small Rust client for Cloudflare WARP built on MASQUE / Connect-IP (HTTP/3). This project packages it for OpenWrt 25.12 with a LuCI app, a procd service and a signed apk feed. It connects in TUN mode and — unlike the first release — does not touch your routing until you opt in: each connection decides whether traffic should use the tunnel.

What it is

Cloudflare WARP is Cloudflare's consumer VPN-ish service. usque speaks its MASQUE transport directly and bridges it to a Linux TUN interface. This port wires the client into OpenWrt's service manager, firewall and web UI — and separates two things that used to be bundled together: connecting the tunnel and routing traffic into it.

Safe by default: no route takeover. Installing and starting usque creates the tunnel but leaves your default routes, ip rules, DNS and firewall forwarding alone. Traffic uses the tunnel only when you enable Default route for a connection, add your own routes, or turn on the IPv6 routing / LAN IPv6 options. This is a deliberate change from v0.1, where every connection installed a default route immediately.

MASQUE / Connect-IP

Uses Cloudflare's WARP endpoints over HTTP/3 (QUIC) with Connect-IP (RFC 9484) for the tunnel's addresses — no WireGuard required.

One-click registration

The LuCI app generates a WARP device identity per connection: accept the terms, click once, and a config file such as /etc/usque/warp0.json is created.

Routing is opt-in

Each connection has its own Default route switch, off by default. Enable it for a classic full tunnel, or leave it off and route selected prefixes yourself.

Multiple connections

/etc/config/usque holds one config usque section per tunnel, each with its own interface, config file, metrics and routing switches.

IPv6, even on IPv4-only WANs

The tunnel gets IPv6 by default; ipv6_route=auto adds an IPv6 default route only when the router does not have one. A separate LAN option can hand a ULA /64 to your devices via NAT66.

Cloudflare or custom endpoints

mode=cloudflare registers a WARP device for you. mode=custom imports a JSON config for another compatible MASQUE/Connect-IP endpoint.

Small and static

Cross-compiled for musl with LTO and size optimisations, stripped, and packaged as an apk: roughly 3 MB installed together with the LuCI app.

TUN mode only

SOCKS5, HTTP proxy, port-forwarding and the HTTP/2 fallback transport were removed to keep the binary small. The router routes packets; nothing else to configure.

Two states: connected vs. routed

Default: connected, routing untouched

  1. LAN clients
  2. Router WAN
  3. The internet exactly as before

The tunnel interface exists and is up, but no default route, policy rule or DNS change is installed — nothing is sent through it.

Opt-in: Default route enabled

  1. LAN clients
  2. Router firewall forward + masquerade
  3. warp0 TUN default route, chosen metric
  4. Cloudflare WARP MASQUE over UDP/443
  5. The internet

The hook also installs an endpoint bypass route via the WAN and a high-priority policy rule; both are removed when the tunnel stops.

Install

Run these on the router over SSH. The feed is a signed apk repository served from GitHub Pages. Installing the packages does not start a tunnel and does not change any routing — you configure and opt in afterwards.

Back up first. Once you enable routing for a connection, the tunnel adds routes and firewall state while it is up. A quick backup of /etc/config/network, /etc/config/firewall, /etc/config/usque and any /etc/usque/*.json identity is always worthwhile.

First run in LuCI

The LuCI app lists your connections, creates WARP identities, starts the service and shows live status. Routing stays off until you enable it.

  1. Open Services → usque

    In the LuCI menu under Services, pick usque (Cloudflare WARP). You will see a connection list — initially one connection named warp0 — plus service controls, routing switches and diagnostics. Each connection is an independent tunnel with its own interface and config file.

  2. Generate a WARP configuration for the connection

    For the default connection, the WARP account card asks you to create an identity. Enter an optional device name (it shows up in your Cloudflare WARP device list), tick the box accepting Cloudflare's terms, and click Generate WARP configuration.

    Under the hood this runs, for that connection's config file:

    The result is /etc/usque/warp0.json: an anonymous WARP device identity containing a private key and an access token. It is created with owner-only permissions — treat it like a password and never publish it. Ticking the box is what accepts Cloudflare's WARP terms; if you skip the UI and just start the service with auto_register=1, the init script registers a device for you and accepts the terms implicitly.

    Registration needs working internet. It happens over HTTPS to Cloudflare through your normal WAN before the tunnel exists, so the router must already be online (and its clock roughly correct) when you press the button.

  3. Enable and start

    Turn on Enable usque service (stored as the connection's enabled option), click Save & Apply, then press Start. The status card should switch to running within a few seconds, and the connection's interface (warp0) appears with its tunnel address.

    The init script only starts connections whose enabled option is set: if you press Start while it is disabled, nothing happens and the app tells you to enable it first. The same applies to /etc/init.d/usque start.

  4. Verify the tunnel

    With the service running, the connection shows its state, addresses and the last connection error (if any). The app's connection test runs a probe from the router:

    With routing still off, this reports warp=off — that is expected: the tunnel is up but nothing is routed into it yet. Continue with the next step.

  5. Choose whether traffic uses the tunnel

    Open the connection's settings. The routing switches are off/unset by default:

    • Default route (off): send all IPv4 traffic through the tunnel — the classic full-tunnel mode.
    • IPv6 route (auto): install an IPv6 default route only if the router has no IPv6 default route yet. always installs it regardless; off never does.
    • LAN IPv6 (off): global switch that hands LAN devices a ULA /64 and NAT66s it through the tunnel.

    Save & Apply (which restarts the connection), then re-run the check above. With Default route on it should now report warp=on and a Cloudflare egress IP. Details and manual alternatives are in Routing.

Registration is per connection and per device. Each generated identity counts as one device in your Cloudflare WARP account. Keep the JSON file if you want to reinstall or move the router without registering again.

Routing: what changes, and only when you ask

usque has two independent layers: establishing the tunnel (always) and sending traffic into it (opt-in). This section describes exactly what each switch changes on the network, so there are no surprises.

Defaults change nothing. A fresh install with defaults installs no default route, no ip rule and no DNS change. The tunnel interface is created, the firewall zone and forwardings are prepared, and the daemon waits — the router keeps routing exactly as it did before. Stop or disable always removes everything usque added.

Routing options

SettingDefaultWhat it changes while connected
default_route (per connection) 0 (off) When on: installs ip route replace default dev <iface> metric <metric> for IPv4. The existing WAN default route is kept, so a failing tunnel falls back to the WAN instead of taking the router offline. Removed when the connection stops.
metric (per connection) 0 Metric used for the tunnel default route(s). Lower wins; with two connections routing by default, give them different metrics to control priority.
ipv6 (per connection) 1 (on) Gives the tunnel an IPv6 address. Set to 0 to keep the tunnel IPv4-only and skip all IPv6 routing for that connection.
ipv6_route (per connection) auto auto: install an IPv6 default route via the tunnel only if the router has no existing IPv6 default route (so IPv4-only/CGNAT WANs get IPv6, native IPv6 is left untouched). always: install it regardless — this can override a native IPv6 uplink. off: never install one.
lan_ipv6 (global) 0 (off) Announces a ULA /64 on the LAN (router advertisements) and NAT66s it through the tunnel, so LAN devices get IPv6 on an IPv4-only WAN. Local ULA only — devices are not globally reachable. Off by default; see LAN IPv6.
lan_ipv6_prefix (global) empty ULA /64 announced when lan_ipv6 is on. Leave empty to use the derived default prefix; set it if you already use a ULA range.
Firewall zone always prepared A dedicated usque zone on the tunnel device (input REJECT, output ACCEPT, forward REJECT) with masquerading (IPv4 + IPv6) and MSS/MTU fixing, plus forwarding into it from every internal zone that forwards to wan (always lan, and e.g. guest). Preparing the zone does not redirect traffic; the wan zone is never modified.
Endpoint bypass when routing is on A host route to the WARP endpoint via the current WAN, installed before any default route so tunnel packets can reach Cloudflare. Only needed — and only installed — when usque actually installs routes.
Policy rule when routing is on ip rule priority 1000 from all lookup main (plus the IPv6 equivalent when an IPv6 route is installed) so mwan3-style fwmark rules cannot divert traffic away from the main table. Installed only when default_route is on or an IPv6 route is installed; with defaults, mwan3 is untouched. Removed on stop.
DNS follows routing No DNS setting is changed. LAN clients keep using the router's dnsmasq; its upstream queries follow whatever default route you chose. With defaults, DNS behaves exactly as before; with Default route on, resolution goes through the tunnel.
Stop / disable — Removes the tunnel routes, endpoint bypass and policy rules, then restores the saved WAN default route if none is left. Your WAN routing and LAN access to the router keep working throughout.

How do I get traffic through the tunnel?

  1. Recommended: enable Default route

    Turn on Default route in the connection's settings (or set default_route='1' in UCI) and save. That is the classic full-tunnel mode: forwarded LAN traffic and router-originated traffic use the tunnel, with the WAN kept as fallback.

    The UCI example assumes the default connection is called warp0; adjust the section name if you renamed it.

  2. Route only selected prefixes yourself

    With Default route off, the tunnel device is a normal interface — add your own routes for the destinations you want tunneled. usque does not manage these, so re-add them after a restart (or script them in a hotplug file):

    This also makes the tunnel interface usable by other routing software (mwan3, VPN policy routing, custom nftables marks) without usque touching the main table.

  3. Use policy routing

    For per-client or per-protocol tunnelling, combine the tunnel device with your own ip rule/nftables marks (or mwan3). Keep in mind that if you later enable Default route, usque installs the priority-1000 rule that makes the main table authoritative while the tunnel is up — stop the service if you need your own policy rules to win.

  4. IPv6

    IPv6 needs no route to connect, but traffic needs one to be routed. With ipv6_route=auto (default) a tunnel IPv6 default route is installed only when the router has none. Use always to force it, or off to leave IPv6 routing untouched. To give LAN devices IPv6 on an IPv4-only WAN, see LAN IPv6.

LAN IPv6 (ULA + NAT66)

On an IPv4-only WAN (common with CGNAT, tethering or DS-Lite), LAN devices have no IPv6. With lan_ipv6=1 usque announces a unique local /64 on the LAN via router advertisements and NAT66s it through the tunnel, so devices get working IPv6 to the internet.

AspectDetails
Requiresodhcpd (default OpenWrt image), a tunnel that supports IPv6, and a free firewall/NAT66 path. The prefix is local/ULA — devices are not globally reachable.
Prefixlan_ipv6_prefix if you set one; otherwise a ULA /64 is derived automatically. Existing static IPv6 assignments on the LAN can conflict — use a matching prefix.
Side effectsRouter advertisements are sent on the LAN; NAT66 prevents inbound IPv6 connections; any existing ULA/RA/DHCPv6 setup should be reviewed before enabling. Turn it off if you already have native IPv6 on the LAN.
DisableSet lan_ipv6='0' and restart the service; the advertisements stop and routes are withdrawn.

mwan3 and other policy routing

By default, usque does not install any policy rule, so mwan3 keeps working normally. Only when Default route is enabled — or an IPv6 route is installed — does the hook add ip rule priority 1000 from all lookup main (and its IPv6 counterpart), because otherwise mwan3's fwmark rules can silently send traffic to the WAN while the tunnel looks healthy. The rule is removed when the tunnel stops. If you need mwan3's per-WAN policies while the tunnel is up, stop the service or leave Default route off and route only selected prefixes yourself.

What WARP is not. WARP changes your apparent egress IP to Cloudflare and encrypts traffic between your router and Cloudflare's edge. It is not an anonymity tool, it does not hide your traffic from Cloudflare, and it is not a substitute for a commercial VPN. Cloudflare's own terms apply to the WARP service.

Custom MASQUE / Connect-IP endpoints

Set mode='custom' to skip Cloudflare registration and use credentials you already have. The connection's config file uses the same JSON layout as a WARP config, with the fields below; there is no registration in this mode.

The endpoint must speak a compatible MASQUE/Connect-IP service. Custom connections are not registered or re-registered by the init script, and auto_register does nothing for them.

Config files and identities

Each connection points at its own JSON file (for the default connection: /etc/usque/warp0.json). In Cloudflare mode it holds the device's private_key and access_token; in custom mode it holds the fields listed under custom mode. Files are written with mode 600 (root only).

  • Back one up off-device to keep the same WARP device across reinstalls: cp /etc/usque/warp0.json /tmp/ and copy it away.
  • Delete it to force a fresh registration: rm -f /etc/usque/warp0.json then restart (with auto_register=1) or press Re-register in LuCI.
  • Never share it — anyone with the file can use your WARP identity.

Troubleshooting

Start with logread -e usque | tail -n 40 — the daemon logs connection and routing decisions. The cases below cover most installs.

usque is running but nothing is routed — is it broken?

No — that is the default. With default_route='0' the tunnel is connected but no traffic is sent into it. To route everything, enable Default route for the connection (or uci set usque.warp0.default_route='1'; uci commit usque; /etc/init.d/usque restart), or add your own routes for selected prefixes. Check with:

Traffic still exits via my ISP while routing is enabled (warp=off)

This is the policy-routing trap: mwan3 (or any fwmark/IP-rule based policy routing) can be evaluated before the main table and silently send traffic to the WAN, even though ip route get shows the tunnel. When routing is enabled, usque installs a priority-1000 rule to prevent it. Check that it is present:

logread -e usque should contain installed IPv4 policy rule: priority 1000 from all lookup main. On stop the rule is removed again — mwan3 keeps working normally when the tunnel is off.

IPv6 is connected but hosts still have no IPv6 route

With ipv6_route='auto' (default) usque only installs an IPv6 default route when the router does not already have one. A leftover or provider-assigned IPv6 default route therefore wins and is left untouched by design. Inspect and choose:

For LAN devices on an IPv4-only WAN you additionally need lan_ipv6 (next entry) — a tunnel IPv6 route alone does not give clients addresses.

LAN devices got no IPv6 addresses

lan_ipv6 is off by default. When enabled it advertises a ULA /64 on the LAN and NAT66s it through the tunnel. Check the switch (global, applying to all connections), that odhcpd is running, and that the prefix does not collide:

If you already run native IPv6 on the LAN, leave lan_ipv6 off — the tunnel should not compete with your existing RA/DHCPv6 setup.

Only one of my connections is used, or routes flap between them

Only one IPv4 default route can win, and one IPv6 default route can win. If two connections both have Default route enabled, give them different metric values (lower wins), or enable routing on just one of them and route other prefixes manually. Check the interfaces and routes:

A custom (non-Cloudflare) connection does not connect

Custom mode skips registration and uses what is in the JSON file. Common causes: wrong or expired keys, the endpoint unreachable over UDP/443, or a missing sni when the provider requires TLS SNI. Check logread -e usque for handshake errors, verify the file layout against custom mode, and confirm the same credentials work with another client. Remember: auto_register has no effect in custom mode.

The LuCI menu entry “usque” is missing after installation

Then hard-refresh the browser (Ctrl/Cmd+Shift+R), log out and back in. Confirm the package is really present with apk info -e luci-app-usque and that /usr/share/luci/menu.d/luci-app-usque.json exists.

The service will not start, or a connection never comes up

Work through these in order:

  1. logread -e usque | tail -n 40 — read the last error.
  2. Is the connection enabled? uci show usque | grep -E 'enabled|interface'. The init script only starts connections with enabled=1.
  3. Is there an identity (Cloudflare mode)? ls -l /etc/usque/warp0.json. If it is missing, either enable auto_register or register from LuCI / the CLI.
  4. Is the clock right? date. A router whose time is far off cannot complete TLS. Let NTP sync (/etc/init.d/sysntpd restart) or set the time in LuCI.
  5. Is TUN available? lsmod | grep tun and ls -l /dev/net/tun. Install the module with apk add kmod-tun and reboot.
  6. If the log says could not resolve route to endpoint, the hook deliberately left your default routes untouched (safe). Check that the WAN has a default route and a reachable gateway, then restart the service.
  7. Is UDP/443 blocked? The tunnel needs UDP/443 to Cloudflare's WARP endpoints (the config file lists them, e.g. 162.159.198.2). Some tethering, hotel, corporate or ISP setups block it. This build is trimmed to QUIC and has no TCP fallback — if UDP is blocked it cannot connect, and you need a WARP client with HTTP/2 support such as the Go implementation of usque.
“UNTRUSTED signature” when running apk update / apk add

The index signature does not match any key in /etc/apk/keys/. Re-download the key, check the fingerprint, and run apk update again. With apk v3 the key is identified by its public-key identity (the filename does not have to be usque.pem, but the key material must match the one the feed was signed with). If the feed was re-keyed, remove the stale key file first. The --allow-untrusted fallback is a last resort only.

apk fails with “No space left on device”

The binary is a few megabytes and some routers have a tiny overlay. Check the space and free some up:

Remove packages you do not use (apk del <name>), clear the LuCI cache (rm -f /tmp/luci-indexcache*), or move the overlay to a USB stick with extroot if your device supports it. A 16 MB-flash router will usually struggle to fit a multi-megabyte binary; a device with more flash is a better fit.

Device limit, or re-registering creates a new device every time

Every Generate WARP configuration registers a new device in your Cloudflare WARP account, and the free plan only allows a limited number of linked devices. This applies per connection: each Cloudflare connection with its own identity is another device. Reuse an existing JSON file instead of re-registering, or remove unused devices in the Cloudflare WARP dashboard / Zero Trust device list. If registration fails with a device-limit error, delete the old device first and try again.

LAN clients are not using the tunnel

The tunnel only affects traffic that follows the router's default route or your own routes. Check that the connection has Default route enabled (or that your static policy routes apply), that the usque firewall zone and forwardings exist (fw4 print | grep -A4 usque; lan and any other internal zone that forwards to wan are wired up automatically), and that clients use the router as their gateway and DNS server. A client with a static public DNS or its own VPN bypasses the router's tunnel. Also check the priority-1000 ip rule if you run mwan3.

Slow or unstable connection

Try, one change at a time: lower the MTU to 1380 (mobile uplinks), check CPU load — encryption at a few hundred Mbit/s is a lot for a small router — and make sure UDP/443 is not throttled or blocked by your ISP. logread -e usque shows reconnect attempts.

Does it break SSH access to the router?

No. Routing changes only affect outbound/forwarded traffic; inbound SSH and LuCI on the LAN continue to work. With defaults, routing is not touched at all. If you manage the router from outside the LAN, keep a reliable out-of-band path before enabling Default route.

FAQ

Does installing usque change my routing?

No. With the v2 defaults, installing and starting usque creates the tunnel but leaves your default routes, ip rules, DNS and firewall forwarding unchanged. Traffic only enters the tunnel after you enable Default route for a connection, add your own routes, or enable the IPv6 routing options.

Why did the first release take over my routes?

v0.1.x always installed default dev <iface> metric 0 on connect. That was convenient for a full tunnel but surprising if you did not expect it. v2 makes routing an explicit per-connection choice, keeps the WAN default route as a fallback, and removes everything it added on stop.

Do I need a Cloudflare account?

No. Registration creates an anonymous free WARP device identity; usque talks to the public WARP service. No Cloudflare login is involved.

How do I route only some traffic through the tunnel?

Leave Default route off and add your own routes for the prefixes you want tunneled (ip route add <prefix> dev warp0), or use policy routing (mwan3, nftables marks, ip rule). See How do I get traffic through the tunnel?. This replaces the old "split tunnelling is not supported" limitation.

Can I use more than one tunnel at a time?

Yes. Add another config usque section (or use the LuCI connection list) with its own interface name and config file. If you want both to route by default, give them different metric values — only one default route can win per address family. See Multiple connections.

Can I use a non-Cloudflare MASQUE/Connect-IP endpoint?

Yes, with mode='custom': provide the endpoint addresses, endpoint public key, your private key and the assigned tunnel addresses in the connection's JSON config. There is no registration in this mode. See custom endpoints.

Is WARP+ or Zero Trust supported?

The LuCI app and the Cloudflare mode focus on the free consumer WARP service. No license-key or organisation/Zero Trust fields are exposed. Custom mode is for other compatible MASQUE/Connect-IP endpoints.

Will it survive a reboot / apk upgrade?

Yes. Connections with enabled=1 start at boot, and identity files persist. Feed updates show up as normal package upgrades (apk upgrade) and keep your configuration.

Which routers are supported?

Right now the feed only contains arm_cortex-a7_neon-vfpv4 packages (ipq40xx/generic) built against OpenWrt 25.12.6. That is also the architecture the tunnel and routing were verified on, using a live OpenWrt 25.12.6 router. Other targets would need their own build — the workflow is in the repository if you want to add one.

Does the router still use my local DNS server (Pi-hole, AdGuard) on the LAN?

Yes — LAN clients can query whichever DNS server you advertise via DHCP. Queries from the router itself, and upstream queries from dnsmasq, follow the routing you chose. A separate LAN DNS appliance keeps answering local clients directly, but its own upstream traffic is only tunneled if it is routed through the router.

Where do I report bugs?

For this packaging (LuCI app, init script, apk feed) use the GitHub issue tracker. Bugs in the tunnel client itself belong upstream at FireMasterK/usque-rs.

Uninstall & cleanup

Stopping the service restores normal routing. Removing the packages cleans up everything except your saved configuration and identities.

WhatAfter uninstall
Binary, init script, hook, helpersRemoved.

Routes, policy rules, run stateRemoved on stop (and by a fallback in the init script). Transient state lives in /var/run/usque/ and disappears on reboot.

If you removed the package files by hand or a stale zone remains, check uci show firewall | grep -i usque, delete the matching sections with uci delete firewall.<section>, uci commit firewall and fw4 reload.

Remove old identities before re-registering elsewhere. If you move to a new router, keep the JSON files and reuse them — that avoids burning another device slot in your WARP account.

Changes compared to upstream

The vendored client is trimmed and adapted to keep the binary small and make it manageable by procd/LuCI: TUN mode only (SOCKS5, HTTP proxy and port-forwarding code removed), QUIC-only transport (the HTTP/2 fallback is removed to save space), no BoringSSL (QUIC via ring, which supports 32-bit ARM), non-interactive register --accept-tos --force, and a size-optimised release profile. Multi-connection management, opt-in routing, IPv6 route selection and LAN IPv6/NAT66 are implemented in this repository's OpenWrt init script, routing hook and LuCI app rather than in the tunnel client. Details are recorded in build/PATCHES.md and UPSTREAM.md.
