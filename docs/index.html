usque · MASQUE / Connect-IP client

Cloudflare WARP for your OpenWrt router.

usque is a Rust client for Cloudflare WARP built on MASQUE / Connect-IP (HTTP/3). This project packages it for OpenWrt 25.12 as a small static binary with a LuCI app, a procd service and a signed apk feed. Install it, generate a WARP identity from the web UI, and route your whole network through it.

  • arm_cortex-a7_neon-vfpv4

What it is

Cloudflare WARP is Cloudflare's consumer VPN-ish service. usque speaks its MASQUE transport directly and bridges it to a Linux TUN interface, so the router can send all forwarded traffic through Cloudflare. This port keeps the daemon lean and wires it into OpenWrt's service manager, firewall and web UI.

MASQUE / Connect-IP

Uses Cloudflare's WARP endpoints over HTTP/3 (QUIC), with Connect-IP (RFC 9484) for the tunnel's addresses — no WireGuard required.

One-click registration

The LuCI app generates a WARP device identity for you: accept the terms, click once, and /etc/usque/warp0.json is created.

Full-tunnel routing

While connected, a default route pointing at warp0 wins while the WAN default route stays in place for automatic failover.

Small and static

Cross-compiled for musl with LTO and size optimisations, stripped, and built into an apk package — roughly 3 MB installed.

TUN mode only

SOCKS5, HTTP proxy and port-forwarding modes were removed from this build to keep the binary small. The router routes packets; nothing else to configure.

Reversible

Stopping the service removes the tunnel routes immediately. Your WAN routing and LAN access to the router keep working.

How traffic flows

  1. LAN clients
  2. Router firewall forward + masquerade
  3. warp0 TUN default route, metric 0
  4. Cloudflare WARP MASQUE over UDP/443
  5. The internet

The WARP endpoint itself is reached with a dedicated bypass route through your normal WAN, so tunnel packets never loop back into the tunnel.

Install

Run these on the router over SSH. The feed is a signed apk repository served from GitHub Pages. Everything below is copy-pasteable.

Back up first. This project changes routing and firewall state while the tunnel is up. A quick backup of /etc/config/network, /etc/config/firewall and an existing /etc/usque/warp0.json is always worthwhile.

Step by step

  1. Install the feed's public key

    apk verifies every repository index against the keys installed in /etc/apk/keys/. In apk v3 the key is matched by its public-key identity, so the filename is not significant; we use usque.pem so it stays recognisable and matches the commands on this page.

    If wget is missing or fails with a TLS error, use uclient-fetch -O /etc/apk/keys/usque.pem <same URL> instead.

  2. Add the repository

    OpenWrt's apk keeps extra repositories in /etc/apk/repositories.d/*.list. Append the feed's index URL:

    Running this twice adds the line twice — harmless, but remove duplicates if you want a tidy file. The URL points directly at the packages.adb index (ndx repository type in apk v3); package files are then fetched from the same /feed/ directory, which is why the feed is flat.

  3. Refresh and install

    The luci-app-usque package depends on usque and kmod-tun, so one command installs the daemon, the init script, the UCI configuration and the LuCI view. For a CLI-only setup use apk add usque.

  4. Open LuCI

    Go to Services → usque and continue with First run. The direct URL is http://192.168.1.1/cgi-bin/luci/admin/services/usque (adjust the router IP).

The feed index (packages.adb) is signed with an ECDSA P-256 key. The matching public key is what you downloaded to /etc/apk/keys/usque.pem and is also committed in the repository as keys/usque.pem. Verify the download if you want to be sure:

If the two hashes match, the key you installed is the one the feed is signed with. If the feed is ever re-keyed, this page is updated with the new fingerprint. You can also verify an individual package file that you downloaded yourself with apk verify <file.apk>.

If the key is missing or does not match the index signature, apk refuses with an UNTRUSTED signature error. Fix the setup rather than bypassing it — but if you are stuck (for example, the key download was intercepted or the feed was rebuilt), you can install without verification as a last resort:

--allow-untrusted disables signature checking for that transaction. Only use it with artifacts you obtained over a trusted connection, and remove the repository afterwards if you cannot restore proper verification.

First run in LuCI

The LuCI app can create the WARP identity, start the service and show the live tunnel status — no JSON editing required.

  1. Open Services → usque

    In the LuCI menu under Services, pick usque. If the entry is missing, see the LuCI troubleshooting note.

  2. Generate a WARP configuration

    With no identity present, the WARP account card asks you to create one. Enter an optional device name (it shows up in your Cloudflare WARP device list), tick the box accepting Cloudflare's terms, and click Generate WARP configuration.

    Under the hood this runs:

    The result is /etc/usque/warp0.json: an anonymous WARP device identity containing a private key and an access token. It is created with owner-only permissions — treat it like a password and never publish it.

    Registration needs working internet. It happens over HTTPS to Cloudflare through your normal WAN before the tunnel exists, so the router must already be online (and its clock roughly correct) when you press the button. Registration usually takes a few seconds.

  3. Enable and start

    Turn on Enabled (this is usque.main.enabled), click Save & Apply, then press Start. The status card should switch to running within a few seconds, and warp0 appears as an interface.

  4. Check the connection

    The overview shows whether WARP is on, your egress IP and the Cloudflare colo (edge location) that serves you. There is also a connection check in the app that runs the same probe from the router — or run it yourself:

    warp=on means the request left through WARP. If it says warp=off, see Troubleshooting.

Registration is per device. Each generated identity counts as one device in your Cloudflare WARP account. Keep /etc/usque/warp0.json if you want to reinstall or move the router without registering again.

What it changes on the network

While the service is running, the router becomes a full-tunnel WARP gateway. Everything below is installed and removed automatically by the init script and its connect/disconnect hook.

AreaBehaviour
Interface warp0 TUN device, MTU 1400 by default (configurable).
Default route ip route replace default dev warp0 metric 0 is added on connect. The existing WAN default route is kept, so if the tunnel disappears the router falls back to normal internet access instead of going offline.
Endpoint bypass A host route to the WARP endpoint IPs via the current WAN gateway is installed before the default route changes, so the MASQUE packets can actually reach Cloudflare.
Firewall A dedicated usque zone bound to the warp0 device (input REJECT, output ACCEPT, forward REJECT) with masquerading and MSS/MTU fixing, plus forwarding from lan into the zone. Your existing wan zone is not modified.
DNS LAN clients keep using the router's DNS (dnsmasq). Its upstream queries follow the default route, so resolution goes through the tunnel. No separate DNS configuration is needed.
IPv6 Disabled by default. When usque.main.ipv6 is enabled and the WAN has IPv6 connectivity, a matching IPv6 default route via warp0 is installed as well.
Stop / disable Stopping removes the tunnel routes and brings back plain WAN routing immediately. SSH access to the router, LAN traffic and the LuCI page are unaffected.
Reboot With enabled=1 the service starts at boot and re-uses the saved identity. With auto_register=1 a missing config file is registered automatically at first start.

What WARP is not. WARP changes your apparent egress IP to Cloudflare and encrypts traffic between your router and Cloudflare's edge. It is not an anonymity tool, it does not hide your traffic from Cloudflare, and it is not a substitute for a commercial VPN. Cloudflare's own terms apply to the WARP service.

All LAN clients are affected while the tunnel is up, because they use the router's default route. Local (LAN) destinations are not tunneled.

The WARP identity file

/etc/usque/warp0.json holds your device's private_key and access_token. It is written with mode 600 (root only).

  • Back it up off-device if you want to keep the same WARP device across reinstalls: cp /etc/usque/warp0.json /tmp/ and copy it away.
  • Delete it to force a fresh registration: rm -f /etc/usque/warp0.json then restart (with auto_register=1) or press Re-register in LuCI.
  • Never share it — anyone with the file can use your WARP identity.

Troubleshooting

Start with logread -e usque | tail -n 40 — the daemon logs why it cannot connect. The cases below cover most installs.

The LuCI menu entry “usque” is missing after installation

The package is installed but LuCI's cached menu index still needs a refresh:

Then hard-refresh the browser (Ctrl/Cmd+Shift+R), log out and back in. Confirm the package is really present with apk info -e luci-app-usque and that /usr/share/luci/menu.d/luci-app-usque.json exists.

The service will not start, or starts but WARP never connects

Work through these in order:

  1. logread -e usque | tail -n 40 — read the last error.
  2. Is there an identity? ls -l /etc/usque/warp0.json. If it is missing, either enable auto_register or register from LuCI / the CLI.
  3. Is the clock right? date. A router whose time is far off cannot complete TLS. Let NTP sync (/etc/init.d/sysntpd restart) or set the time in LuCI.
  4. Is TUN available? lsmod | grep tun and ls -l /dev/net/tun. Install the module with apk add kmod-tun and reboot.
  5. Is UDP/443 blocked? Test the HTTP/2 fallback: enable it in LuCI or uci set usque.main.http2='1'; uci commit usque; /etc/init.d/usque restart. HTTP/2 support is compiled into the default build; if the option has no effect, check the release notes for slim variants.
“UNTRUSTED signature” when running apk update / apk add

The index signature does not match any key in /etc/apk/keys/. Re-download the key, check the fingerprint, and run apk update again. With apk v3 the key is identified by its public-key identity (the filename does not have to be usque.pem, but the key material must match the one the feed was signed with). If the feed was re-keyed, remove the stale key file first. The --allow-untrusted fallback is a last resort only.

No internet after stopping or uninstalling the tunnel

If a stale default route survived a crash, restore normal routing:

Also check for leftovers with ip -6 route when IPv6 was enabled. Rebooting always brings you back to a clean state.

apk fails with “No space left on device”

The binary is a few megabytes and some routers have a tiny overlay. Check the space and free some up:

Remove packages you do not use (apk del <name>), clear the LuCI cache (rm -f /tmp/luci-indexcache*), or move the overlay to a USB stick with extroot if your device supports it. A 16 MB-flash router will usually struggle to fit a multi-megabyte binary; a device with more flash is a better fit.

“Generate WARP configuration” fails

Registration is a normal HTTPS request through your existing WAN connection, so it cannot work while the router itself has no internet. Check, in this order: ping 1.1.1.1, DNS (nslookup www.cloudflare.com), the system time (date), then the daemon log. If the WAN is up and the clock is right, retry — Cloudflare sometimes rate-limits registrations, so wait a minute rather than clicking repeatedly.

On the command line the same action is usque --config /etc/usque/warp0.json register --accept-tos --force -n "my-openwrt", which prints the actual error.

Device limit, or re-registering creates a new device every time

Every Generate WARP configuration registers a new device in your Cloudflare WARP account, and the free plan only allows a limited number of linked devices. Reuse an existing /etc/usque/warp0.json instead of re-registering, or remove unused devices in the Cloudflare WARP dashboard / Zero Trust device list. If registration fails with a device-limit error, delete the old device first and try again.

LAN clients are not using the tunnel

The tunnel only affects traffic that follows the router's default route. Check that the usque firewall zone and the lan → usque forwarding exist (fw4 print | grep -A4 usque) and that clients use the router as their gateway and DNS server. A client with a static public DNS or its own VPN bypasses the router's tunnel.

Slow or unstable connection

Try, one change at a time: lower the MTU to 1380 (mobile uplinks), switch between QUIC and the HTTP/2 fallback, and check CPU load — encryption at a few hundred Mbit/s is a lot for a small router. logread -e usque shows reconnect attempts.

Does it break SSH access to the router?

No. The tunnel only changes the default route for outbound/forwarded traffic; inbound SSH and LuCI on the LAN continue to work. If you are managing the router from outside the LAN, stop the service or keep a reliable out-of-band path before experimenting.

Stopping the service is enough to restore normal routing; removing the packages cleans up everything except your saved configuration.

FAQ

Do I need a Cloudflare account?

No. Registration creates an anonymous free WARP device identity; usque talks to the public WARP service. No Cloudflare login is involved.

Which routers are supported?

Right now the feed only contains arm_cortex-a7_neon-vfpv4 packages (ipq40xx/generic) built against OpenWrt 25.12.6. This is the only architecture that is built and exercised so far; other targets would need their own build — the workflow is in the repository if you want to add one.

Is WARP+ or Zero Trust supported?

The LuCI app and this build focus on the free consumer WARP service. No license-key or organisation/Zero Trust fields are exposed.

Will it survive a reboot / apk upgrade?

Yes. With enabled=1 the procd service starts at boot, and the identity file persists. Feed updates show up as normal package upgrades (apk upgrade) and keep your configuration.

Can I exclude some traffic from the tunnel (split tunneling)?

Not in this version. The tunnel uses the default route, so all forwarded traffic goes through it while the service is running. Stop the service to return to normal routing. Traffic to the local LAN is never tunneled.

Does the router still use my local DNS server (Pi-hole, AdGuard) on the LAN?

Yes — LAN clients can query whichever DNS server you advertise via DHCP. Queries from the router itself, and upstream queries from dnsmasq, follow the tunnel while it is up. A separate LAN DNS appliance keeps answering local clients directly, but its own upstream traffic is only tunneled if it is routed through the router.

Is this an official Cloudflare or OpenWrt project?

No. It is an independent packaging of the open-source usque-rs client. See the source section for licences and disclaimers.

Where do I report bugs?

For this packaging (LuCI app, init script, apk feed) use the GitHub issue tracker. Bugs in the tunnel client itself belong upstream at FireMasterK/usque-rs.

Build pipeline

  1. Build the binary — cross-compilation to armv7-unknown-linux-musleabihf with a static musl toolchain, LTO and opt-level="z", then stripped. See the workflows (build.yml) and build/build-usque.sh.
  2. Package & sign — the OpenWrt 25.12.6 SDK builds usque and luci-app-usque; scripts/ assembles the feed and signs packages.adb with an ECDSA P-256 key (package.yml).
  3. Publish — publish.yml copies docs/ to the site root, puts the public key and the signed feed into /feed/, and deploys the artifact to GitHub Pages.

Build it yourself by cloning the repository and following the workflow files — the packaging is deliberately plain OpenWrt makefiles plus a GitHub Actions pipeline, no local OpenWrt checkout is committed.

Patches to upstream

The vendored client is trimmed and adapted to keep the binary small and make it manage-able by procd/LuCI: TUN mode only (SOCKS5, HTTP proxy, port-forwarding code removed), no BoringSSL (QUIC via ring, which supports 32-bit ARM), non-interactive register --accept-tos --force, and a size-optimised release profile. The connect/disconnect hook, init script and LuCI app are added in openwrt/. Details are recorded in build/PATCHES.md and UPSTREAM.md.
